## 決定 1：第二個 controller 實例（align_controller，max_vel_x = 0）

### 1. Nav2 Humble 是否支援多個 controller plugin、FollowPath 是否有 controller_id

**支援。** 查證依據（這台開發機上安裝的 `ros-humble-nav2-controller 1.1.20`）：

| 依據 | 內容 |
|---|---|
| `ros2 interface show nav2_msgs/action/FollowPath` | goal 欄位：`nav_msgs/Path path`、**`string controller_id`**、**`string goal_checker_id`** |
| `/opt/ros/humble/include/nav2_controller/controller_server.hpp` | 成員 `controller_ids_`、`controller_types_`、`default_ids_`、`findControllerId(c_name, name)` —— 以 id 查 plugin，與 `goal_checker_ids_` / `findGoalCheckerId` 同一套 |
| `libcontroller_server_core.so` 內的錯誤字串 | `FollowPath called with controller name %s, which does not exist. Available controllers are: %s.`（goal checker 有同樣一句） |
| 本專案已在用同一機制 | `nav2_params.yaml` 的 `goal_checker_plugins: ["general_goal_checker", "approach_goal_checker"]`；manager 每段送 `goal_checker_id`（階段 25 起） |

**注意事項（由上面的錯誤字串推得）**：controller 變成兩個之後，`controller_id` 留空或打錯會被拒絕、該段 ABORTED。
manager（`manager.py:1421`）與 smoke_test 的 NavRig（`smoke_test.py:1834`）都已經明寫 `controller_id = 'FollowPath'`，不會受影響。

### 2. 用 C1 錄到的資料驗算：max_vel_x = 0 時轉不轉得到、會不會沒有可行軌跡

資料：`test/logs/stage38/collision/bag`（與 C1 同設定的擷取趟），割草線 1 開始前後 1.7 s 內的 35 筆 DWB 評估。

**不會卡死。** 35 筆評估每一筆都有 **≥ 20 條有效的原地旋轉候選**（vx = 0），沒有任何一筆是「原地旋轉全部無效」。
原因：BaseObstacle 只看中心點，原地旋轉時中心點不動，只要起點那一格不是 inscribed / lethal 就永遠有效
（起點本身的淨空已由 manager 的 rotation_swept_radius 檢查保證）。

**方向會對。** 割草線開始 +0.30 s 那一筆的 20 條原地旋轉候選（車頭 −115°，目標 0°）：

| wz | 末端朝向 | total | GoalAlign | GoalDist | PathAlign | PathDist | RotateToGoal |
|---|---|---|---|---|---|---|---|
| −1.20 | −165° | 68.4 | 36.0 | 22.8 | 8.8 | 0.8 | 0 |
| −0.57 | −140° | 71.2 | 37.2 | 22.8 | 10.4 | 0.8 | 0 |
| +0.19 | −89° | 67.2 | 34.8 | 22.8 | 8.8 | 0.8 | 0 |
| +0.57 | −53° | 60.8 | 30.0 | 22.8 | 7.2 | 0.8 | 0 |
| +0.95 | −13° | 49.2 | 24.0 | 22.8 | 1.6 | 0.8 | 0 |
| **+1.07** | **+1.7°** | **47.8（最低）** | 23.4 | 22.8 | 0.8 | 0.8 | 0 |
| +1.20 | +15.7° | 50.6 | 24.6 | 22.8 | 2.4 | 0.8 | 0 |

* **GoalDist 對所有原地旋轉都一樣（22.8）**：中心點不動，離目標的距離不變，它不提供方向資訊。
* **GoalAlign / PathAlign 讓末端朝向最接近目標的那一條勝出**（+1.7° 那條最低，衝過頭的 +15.7° 反而變差）。
* 目標方向在 ±90° 外時分數很平（−165° ~ −115° 之間 68 ~ 71 幾乎相同）：轉 180° 左右時，往哪一邊轉可能取決於很小的差距。
  對原地旋轉而言兩邊都安全，Oscillation critic 會防止來回切換。

**這份資料驗證不到的一件事（重要）**：上面的分數是在「目標 = 割草線終點」的情況下算的。
對正階段的目標會是「原地、指定朝向」—— 那時 GoalDist / GoalAlign / PathDist / PathAlign 的「到目標的距離」幾乎都一樣，
**方向只能靠 RotateToGoal**（只在離目標 xy_goal_tolerance 以內時作用，對正階段一開始就在範圍內）。
這一筆資料裡 RotateToGoal 全部是 0（目標在 4.9 m 外），所以**它在對正階段的行為只能從程式邏輯推論，沒有實測**。
要確認需要一趟實驗（加 plugin 的設定改動），等使用者同意後再做。

### 3. 代價：每段多一個對正階段

| 量 | 數值 | 來源 |
|---|---|---|
| 每段開始時的航向差 | 中位 171°、最大 176° | 階段 32 run1，39 段 |
| 現行「邊走邊轉」轉到誤差 < 0.1 rad 的時間 | 中位 3.78 s、總計 160.7 s | 同上 |
| 原地對正的時間（DWB 上限 1.2 rad/s、角加速度 1.5 rad/s²） | 中位 3.29 s、總計 123.6 s | 模型；C1 實測「從靜止原地轉 17° 花 0.51 s」，模型給 0.63 s，模型偏保守 |
| 多一個 goal 的固定開銷 | 段落完成 → 送出 0.001 s、送出 → Nav2 接受 0.002 s | 階段 32 manager.log |
| 階段 32 任務總時間 | 875 s | |

* **上限 +123.6 s（+14 %）**：假設對正階段的時間完全沒有和前進重疊。
* 實際淨增加會小很多：現行的弧線本來就花 3.78 s（中位）在轉向，對正之後割草線起步就是直的，
  省下的是弧線途中那段「斜著走」的距離。淨效果介於 −37 s（弧線的前進完全沒用）與 +124 s 之間，量級是**每段數秒、整趟 1 ~ 2 分鐘以內**。
  要精確的數字需要實測。

### 4. 失敗模式

| # | 失敗模式 | 會發生什麼 | 備註 / 需要的處理 |
|---|---|---|---|
| **1** | **對正用 `approach_goal_checker` 會假成功** | 它的 `yaw_goal_tolerance: 3.15`（= 不看朝向）。對正的目標 xy 就是車子當下位置，**送出的瞬間 xy 達標、朝向不檢查 → 立即 SUCCEEDED，一度都沒轉**。接著主控制器照舊邊走邊轉，撞同一面牆 | **這正是 stateful goal checker 假成功的同一類陷阱**。對正必須用會檢查朝向的 goal checker |
| 2 | 改用 `general_goal_checker`（yaw 0.5 rad = 28.6°） | 對正停在 28.6° 誤差內就算成功。車頭角側向 = 0.42 cos θ + 0.975 sin θ，θ = 28.6° 時 **0.836 m**（比車寬一半多 0.42 m），主控制器在這個誤差下仍會邊走邊轉 | 需要一個更緊的對正專用 goal checker（例：θ = 3° → 0.47 m、5° → 0.50 m）。新增 goal checker plugin 是設定，不是架構，但數值要使用者決定 |
| 3 | 對正卡住 | RotateToGoal 有 `slowing_factor 5`，接近目標時減速；在容忍邊緣來回時角速度可能低於 `min_theta_velocity_threshold`（0.001）以上卻轉不進容忍範圍 | 由下一項的 progress checker 兜底 |
| 4 | **超時：progress checker 只看平移** | `SimpleProgressChecker` 要求 15 s 內移動 0.5 m；**原地旋轉不平移，所以任何對正超過 15 s 都會被判「Failed to make progress」→ ABORTED**。正常 180° 只要約 3.3 s，所以實際上它就是一個 15 s 的對正超時 | 超時之後的處理要定：當成該段失敗（走既有的 skip-and-continue 與連續失敗計數）最一致；不要自動重試對正（「沒有改變任何東西的重試不應該被重試」） |
| 5 | 對正完成到 FollowPath 開始之間漂走 | controller_server 在 goal 結束時送零速度；manager 從收到結果到送出下一段只要毫秒（實測 0.001 ~ 0.002 s）。剩下的漂移是旋轉減速時的慣性與側滑：摩擦掃描實測原地旋轉 8 s 的平移 0.02 ~ 0.11 m | 漂移量級在 xy_goal_tolerance 附近；主控制器起步時誤差小，不會重現 approach 那種 0.36 m 的假成功（那是 stateful 鎖住 xy 之後才轉 171°） |
| 6 | 對正中心點的淨空 | 原地旋轉需要 rotation_swept_radius 1.0616 m 的淨空 | manager 已經對每段起點做這項檢查（`lead_in_point_unsafe(need_rotation=True)`、`start_pose_blocked()`），不需要新邏輯 |
| 7 | approach 本身也是邊走邊轉 | C1 撞牆後的兩次 approach 也失敗；approach 起點的航向差一樣大 | 對正階段要不要也加在 approach 之前，要一起決定 |
| 8 | controller_id 打錯 / 設定漏了 | 每一段 ABORTED → 連續 3 段 → 任務停止 | 失敗得很大聲，Phase N / O / P 會立刻紅 |

**結論**：方向可行（介面存在、不會沒有可行軌跡、方向分數正確），但**第 1、2 點必須先解決**：
對正階段**不能**用 approach_goal_checker，而 general_goal_checker 的 28.6° 太鬆。
第 4 點（progress checker 只看平移）讓對正天然有 15 s 超時，超時的語意要先定好。

## 決定 3：周邊環繞切段規則

### 原因（查明）

`cut_on_direction_change()` 的規則是「相鄰兩步的方向內積 ≤ 0」= **單一步轉角 ≥ 90° 才切**。
它是為 F2C 的割草線設計的：弓字形兩條割草線之間的橫向連接段與割草線**剛好垂直**，單步就是 90°。

stage29_lawn、headland 1.20 時的環繞（355 個航點、35.38 m）：

| 轉角位置 | 各步轉角 | 合計 |
|---|---|---|
| (−4.47, 4.04) | −88°、+42°、−35°、−9° | −89.7° |
| (4.47, 3.98) | −89.5° | −89.5° |
| (3.87, −4.32) | +40°、−39°、**−86°**、+10°、−35°、+60°、−36° | −85.1° |
| (−4.00, −3.64) | +79°、−85°、−50°、−63°、+85° | −34.5° |
| (−4.38, −2.31)（起點） | +63° | |

* **最大單步轉角 89.5°，沒有一步 ≥ 90°** → 一刀都沒切 → 整圈一段 → 起點 = 終點 → goal checker 在送出的當下判定到達。
* 原因不只是「被切成斜角」：SLAM 地圖萃取的邊界本來就不是完美的直角，真正的轉角是 85° ~ 89.5°，
  有的還被分散在好幾步（79° − 46°、40° − 39° − 86° …）。
* **這個缺陷在階段 32 就存在，只是沒有爆**：headland 0.70 時切出 3 段，但第 1 段「周邊環繞 1/3」長 25.47 m、
  跨過好幾個轉角 —— 也是沒切開，只是起點 ≠ 終點，所以 DWB 還是開完了。

**更正：N3 不是同一個根源。** Phase N 用的是理想正方形邊界，環繞的轉角剛好 90°，**正常切成 4 段**（log：「周邊環繞切出 4 段直邊」）。
N3 失敗在環繞第 1 邊（2.3 m）的終點：停在離終點 0.06 m、側偏 0.10 m 處 15 s 沒有進展 —— 那是短邊上收斂不回來，與決定 1（掉頭方式）有關，不是切段。

### 修法提案（未實作）

1. **只對環繞用的轉角偵測**（割草線維持 90° 規則不動，避免動到已驗證的割草線切段）：
   沿路徑累積方向變化，在**一小段弧長內（例如 0.5 m）累積轉角 ≥ 某個門檻（例如 45° ~ 60°）**就視為一個轉角，在該群的中點切開。
   上表的五個轉角群用累積法都會被抓到（合計 34° ~ 90°），直線上的雜訊（單步 1° ~ 10°）不會。
2. **閉合迴圈不得整段送出**：環繞切完如果仍有一段「起點與終點距離 ≤ xy_goal_tolerance」，強制在離起點最遠的航點切成兩段。
   這一條是兜底：就算轉角偵測漏了，也不會再出現「0 秒完成」。
3. **送出前的檢查**（所有段落）：起點 = 終點的段落不送，記錄成錯誤，而不是讓 goal checker 當場判定成功。

門檻（弧長窗口、累積角度）要使用者決定。B5 會在修好後轉綠（現在 0 %，判準 ≥ 90 %）。

### 測試覆蓋的缺口（已補）

新增 **B5「周邊環繞有效長度」**（第 63 項）：用進版控的 stage29_lawn 地圖跑 map_to_boundary → F2C → manager 自己的切段函式，
有效長度 = 各段長度總和、起點 = 終點的段落算 0。判準：規劃長度 > 0 且 ≥ 邊界周長 × 0.5；有效長度 ≥ 規劃長度 × 0.9。

| 組態 | 邊界周長 | 規劃環繞 | 切出 | 起點 = 終點 | 有效 | B5 |
|---|---|---|---|---|---|---|
| headland 0.70（階段 32，用參數覆寫跑） | 48.40 m | 39.27 m | 3 段 | 0 | 39.27 m（100 %） | 綠 |
| headland 1.20（現行） | 48.40 m | 35.38 m | 1 段 | 1 | **0.00 m（0 %）** | **紅** |

先確認舊組態是綠、現行是紅，紅的是真的缺陷。

## O1 的原因（查明，未修）

資料：`test/logs/stage38/o1/`（Phase O 單獨重跑一趟，同一個失敗重現：第一個失敗 = 割草線 5/16），bag 錄 /odom、/tf、local_costmap、/cmd_vel_nav（12 MB，不錄相機）。

| 量 | 值 |
|---|---|
| 失敗的段落 | 割草線 5/16，起點 (−3.95, −2.60)，往東 |
| 進入前的朝向 | 割草線 4 的終點，往西 —— 要掉頭 180° |
| 卡住時 base_link | (−3.67, −1.99)，yaw 35°（**比割草線往北偏了 0.61 m**） |
| 卡住時 cmd | vx 0.70、wz −0.82（邊前進邊順時針轉） |
| 左前角 / 右前角 | (−3.11, −1.09) / (−2.63, −1.78) |
| 箱子 | 中心 (−2.5, −0.75)、x −3.0 ~ −2.0、y −1.25 ~ −0.25 |
| 接觸點 | **箱子西南角 (−3.0, −1.25) 正好落在車頭前緣（左前角 → 右前角）上**：車頭前緣頂住箱角 14 s |

**和撞牆是同一個問題的另一個表現。** 割草線 5 本身離箱子 1.35 m，夾具判定「不會被擋住」（< 車體半寬 0.42 才算），這個判定沒錯 ——
撞上箱子的不是割草線，是**割草線起點的掉頭**：DWB 從朝西經朝北轉到朝東，順時針的弧讓後輪軸往北移 0.61 m，
車頭 0.975 m 再往前甩，前緣碰到箱角。BaseObstacle 只看後輪軸那一點，它離箱子還有 0.7 m 以上。

之後的 approach 從箱子旁邊出發，連續失敗 → 割草線 7 失敗 → 連續 3 段 → 任務中止（O1 的「跳過後完成割草線 = 0 條」）。

O1 的判準（第一個失敗的必須是被箱子擋住的割草線、跳過後要能繼續割）沒有放寬；它紅是因為產品在掉頭時撞上箱子，不是夾具錯。
決定 1 的對正階段如果成立，割草線 5 起點會原地轉 180°（需要 1.0616 m 淨空；起點離箱子 1.35 m，夠），這個碰撞應該消失 —— 待實驗確認。
