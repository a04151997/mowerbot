## 原地旋轉：命令 vs 實際角速度（死區）與停止精度　【實機才量得到，和模擬曲線直接比】

- **為什麼要量**：對正控制器（每段開始前原地轉正）的容忍值 0.10 rad 是**在模擬裡調出來的**，而模擬的低速旋轉已知不可信
  （`stage38_decisions.md` 14 節）。實機量到這三個數字，就知道模擬偏悲觀多少、0.10 該不該收緊。
- **要量什麼**：
  1. **命令 vs 實際曲線**：對 /cmd_vel 直接下固定 wz（不經過 Nav2），+0.02 到 +0.40、每次加 0.02，各 3 s，取後 2 s 的實際角速度；負方向再一次。
  2. **起轉的最小命令值**（從靜止開始，實際角速度 > 0.01 rad/s 的最小 wz），正反兩個方向各一個數字。
  3. **停止精度**：以 0.2 rad/s 旋轉時送零，量之後 1 s 內還轉了多少度。
- **怎麼量**：
  1. 車子架高（輪子離地）先跑一次確認方向與安全，再放到**草地**上跑正式的一次（草地才是作業條件）。
  2. 只開 bridge_node（`read_only:=false`、`max_vel_scale` 1.0），**不開 manager / Nav2**；確認沒有 ROS 1 驅動同時在跑。
  3. 執行 `python3 test/tools/spin_deadband.py <輸出>.csv`（與模擬同一支工具、同一組命令值），結果直接與下面的模擬曲線比。
     角速度用 IMU（若有）或 bridge 的 /odom；兩者都記下來。
  4. 停止精度：`ros2 topic pub` 送 0.2 rad/s 3 s 後送零，錄 /odom 的 yaw。
- **模擬的對照數字**（`test/logs/stage38/spin_deadband_PROVISIONAL.csv`、`spin_deadband_primed_PROVISIONAL.csv`，demo_lawn，腳輪 mu 0.1/0.05）：

  | 命令 wz | 第一次（正向從靜止） | 第一次（反向，接在正向之後） | 預先同向轉過之後（正 / 反） |
  |---|---|---|---|
  | 0.02 | 0.013 | ~0 | ~0 / ~0 |
  | 0.10 | 0.088 | ~0 | ~0 / ~0 |
  | 0.18 | 0.164 | 0.062 | ~0 / ~0 |
  | 0.22 | 0.180 | 0.172 | 0.008 / ~0 |
  | 0.30 | 0.099 | 0.054 | 0.091 / 0.043 |
  | 0.40 | 0.168 | 0.347 | 0.441 / 0.237 |

  - **起轉最小命令值：0.02 ~ 0.28 rad/s，取決於前一個動作**（同一個命令值在不同時刻可以差 10 倍以上）—— 不是單一個死區。
  - **停止精度**：送零之後仍以 0.19 rad/s 轉 1 s（最終誤差 0.15 ~ 0.17 rad）。
  - 原地旋轉時後輪軸平移 0.07 ~ 0.10 m。
- **不量的後果**：對正容忍值 0.10 rad 一直是「模擬能做到的最好」，不是設計值；車頭角在對正誤差 0.10 時多伸出 0.095 m，
  吃掉轉彎餘裕 0.1384 m 的 69 %。實機若停得更準，這個 69 % 可以大幅降低。
- **優先度**：與 lidar_z_ground 同一次去實驗室時做；它和 CLAUDE.md 的凍結條件「實機原地旋轉角速度」是同一組量測。

## lidar_z_ground

- **量什麼**：地面 → **光達開口（掃描窗）的中線**高度。不是光達外殼頂。
- **怎麼量**：
  1. 車停在平地，輪胎正常氣壓、電池接著。
  2. 從**側面**（不要從上面）把捲尺垂直立在光達旁邊的地面上，眼睛與光達窗口同高再讀數。
  3. 同一位置拍一張側面照（看得到捲尺刻度與光達窗口），交回來。
  4. 填 `lidar_z_ground` = 讀數（公尺）；`provenance: measured`。
- **目前值**：0.55，照片目視估計（現有兩次量測都是俯視拍攝，無法取得高度）。
  經過一次自洽性修正（原本 0.70 / 0.55 與 body_height 互相矛盾）。
- **不量的後果**：
  - 實機 launch 會被 `geometry_guard` 擋下（這是刻意的，不要用 override 繞過）。
  - 遮擋是懸崖不是斜率：目前光達比引擎頂、車體頂各高 0.05 m，兩個都是目測。
    只要估錯 5 cm，模擬光達就會從 0° 遮擋跳到 59° ~ 170°（引擎）或 360°（車體）。
- **順便做**：光達驅動起來之後車停空曠處跑 `python3 test/tools/scan_fov.py 4`，把印出的遮擋角度範圍交回來。這是遮擋的直接量測，比任何高度推算可靠。

## lidar_x　【最便宜的一項：不用重量】

- **量什麼**：後輪軸中心（O）→ 光達旋轉中心，沿 x 軸線的距離。
- **只需要確認一件事**：先前量到「後輪區域到光達約 30 ~ 32 cm（台寸換算）」，當時**捲尺 0 刻度勾在哪裡**？
  - (a) 後輪輪心 → 直接用，誤差可收斂到 ±0.02
  - (b) 鋁架後緣 → 要再量「鋁架後緣到後輪輪心」並扣掉
  - (c) 胎面最後端 → 0.30 要減掉 rear_wheel_radius 0.155
  三者相差最多 15.5 cm，這就是目前 uncertainty 0.08 的由來。
  **這一個問題的答案同時解開模型裡的矛盾**：照片描述光達在「引擎與電池之間」（前後分開），
  但目前的估計（引擎以曲軸 0.375 為中心、長 0.35 → x 0.20 ~ 0.55；光達 0.30）讓光達落在引擎前後範圍的正上方。
  若 0 刻度其實勾在胎面最後端（a 以外的情況），光達會往後移，兩者就不矛盾了。
- **怎麼重量（若需要）**：鉛錘從光達頂部中心垂到地面做記號 L，捲尺量 O 到 L 在 x 軸線上的投影。左右偏移也記下來（模型目前假設 0）。
- **目前值**：0.30 ± 0.08（measured_coarse）。
- **不量的後果**：TF 的 x 錯 Δx，每個掃描點都沿車身 x 平移 Δx；目前最大 0.08 m = 1.6 格 costmap。
  原地旋轉時障礙物會在半徑 Δx 的圓上「甩」，scan matching 會看到牆在動。
  另外光達在引擎前 / 後 / 正上方，決定遮擋會不會發生（`stage38_collision_brief.md` 5.2）。

## blade_offset_x

- **量什麼**：後輪軸中心（O）→ 刀盤旋轉中心，沿 x 軸線。
- **怎麼量（從易到難，做第一個就好，有時間再用第二個驗證）**：
  1. **量引擎曲軸中心**：刀盤直接鎖在引擎垂直曲軸上，兩者同心。曲軸從車體上方可見（引擎頂部中央），
     不用鑽到車底。鉛錘從曲軸中心垂到地面做記號 B，量 O 到 B 的 x 投影。
  2. **量刀尖兩次**（自帶檢查）：拔火星塞線，把一支刀轉到正對車尾，鉛錘垂下量到 O 的距離 L1；
     轉到正對車頭量 L2。`blade_offset_x = (L1 + L2) / 2`；**驗證 L2 − L1 ≈ 0.50（割幅）**，差太多就是量錯。
  3. **量刀盤護罩前後緣取中點**（護罩與刀盤同心）。
- **目前值**：0.375 ± 0.025（measured_coarse），實測範圍 0.35 ~ 0.40，刀盤藏在機殼下方無法直接定位圓心。
- **不量的後果**：決定刀片軌跡（blade_link）與引擎方塊的前後位置（同心）。
  **本輪敏感度量不到**：blade_offset_x 0.35 / 0.40 的跑測被取消，因為任務在割草線 1 就撞牆中止
  （`stage38_collision_brief.md`），兩趟只會量到同一個碰撞。判準（差 < 0.5 pt 結案、> 2 pt 列為必測）留到碰撞問題處理之後。

## engine_top_z_ground / engine_bottom_z_ground / engine_width / engine_length

- **量什麼**：Honda GCVxe200 引擎外殼（含油箱、空濾、拉繩把手）最高點 / 最低點離地；在光達掃描面高度的左右寬、前後長。
- **怎麼量**：最高點用捲尺從地面量（通常是油箱蓋或空濾蓋）；寬與長在光達窗口那個高度用鋼尺量。拍側面照。
- **目前值**：頂 0.50 / 底 0.25 / 寬 0.45 / 長 0.35（provisional，照片估計；頂刻意取低於光達，依「現場目視未遮擋」）。
  前後中心不另量，等於刀盤中心（曲軸同心）。
- **不量的後果**：引擎頂高於光達掃描面時遮擋角 = 2·atan(寬/2 ÷ 光達到引擎近面距離)，
  0.05 m 遠時 155°、0.35 m 遠時 66°（`stage38_collision_brief.md` 5.1）。

## body_height

- **量什麼**：地面 → 鋁架甲板（車體方塊頂面）高度。
- **怎麼量**：側面，捲尺從地面量到甲板上緣。
- **目前值**：0.50（provisional，照片目測；自洽性修正後的值）。原廠車身 0.46。
- **不量的後果**：它若 ≥ lidar_z_ground，模擬光達 360° 全瞎；載入器會直接拒絕啟動並指出這兩個值打架。

## rear_wheel_radius（幾何半徑）與滾動半徑

- **目前的 0.155 ± 0.005** 是「輪心到胎面最外緣」的**靜態幾何半徑**（原話「圓心到黑色外框最外面大概 15-16 cm」）。
- **實際滾動半徑會較小**：約 80 kg 車重會把充氣胎壓扁，兩者可能差 5 ~ 10 mm。
- **影響**：base_link 離地高度（光達 z 換算 = lidar_z_ground − rear_wheel_radius）；
  里程計**僅當** /odom 由上位機計算時。若控制板韌體自行計算位姿則不影響 —— 待協定確認後才知道。
- **滾動半徑量法**：
  1. 後輪胎面與地面接觸處各做一個記號（輪子上一個、地上一個）。
  2. 車輛正常載重（**電池接著**，機身警告：未接電池推動會產生逆電流），直線推行，讓該輪恰好轉 **5 圈**。
  3. 量起點到終點的直線距離 D。
  4. 滾動半徑 = D / (5 × 2π)。
- **優先度**：等控制板協定確認後再決定。
- footprint 的誤差：±0.005 傳到 rotation_swept_radius 是 1.0560 ~ 1.0672，headland 仍是 1.20（穩定）。

## body_width_total

- **目前值**：0.840 ± 0.005（「這樣大概是 84 cm，因為有那些鐵架」）。⚠ 原廠 0.73，實測較大是因為加裝鋁架 —— 用實測值，不要改回原廠值。
- **要不要重量**：不急。±0.005 讓 lateral_half_extent 在 0.4175 ~ 0.4225，相較於偏航 10° 造成的 +0.163 m 是 3% 的雜訊。

## front_wheel_radius

- **目前值**：0.100 ± 0.005。**不需要為了 footprint 重量**：它在 front_extent = L − r_rear 的推導裡完全抵消，只影響腳輪在 URDF 的位置。

## com_x / com_height（質心）

- **怎麼量**：三台體重計（兩後輪各一、兩個腳輪一起墊一塊板），三點等高、同時讀數。
  `com_x = 0.875 × 前輪讀數 / 總重`；總重 = 三個讀數相加（順便量了 mass）。
- **目前值**：0.41 / 0.25（provisional）。
- **不量的後果**：後輪分到的重量 = 模擬牽引力上限。

## mass

- **目前值**：73.4（原廠 57.2 + 電池 16.2）。⚠ 加裝鋁架、兩顆減速馬達、編碼器、迷你電腦、光達、控制板後實際應為 82 ~ 86 kg。
- **怎麼量**：同 com_x 那一次，三個讀數相加。
- 本輪 mass 85 探測被取消（任務在割草線 1 撞牆，量不到差異）。

## caster_track / caster_trail / rear_wheel_width / front_wheel_width / body_ground_clearance

低優先（impact low）。鉛錘 + 捲尺：兩個腳輪轉軸中心距、腳輪轉軸到輪軸的水平距離、胎面寬、車架最低點離地。
caster_trail 0.02 是 Gazebo 建模值，量到的實際值若差很多可以換掉。
